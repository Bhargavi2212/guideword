## Goal, and what the video shows

An engineer can do the whole review in the browser: load a plant, confirm sections, start or open a run, watch the agent work, read the shortlist, open a finding to see why each number is what it is, accept/reject/edit, and export. Every number on screen opens the record it came from.

The video (§14, under 3 minutes) is recorded from these screens. Two of its beats need things the backend alone can't give: the **agent timeline** of a run that took about 36 minutes (shown as a labelled replay, P5-4), and the **reboiler moment** (shortlist → detail → override).

## What the code has today (checked on `main` at "Merge pull request #96", 2026-10-22)

**Frontend**
- `frontend/src/` has `App.tsx` (a placeholder), `main.tsx`, `App.test.tsx`, and `api/types.ts` (generated by `openapi-typescript` from `contract/openapi.json`, 3,203 lines, at contract v1.8).
- Dependencies: React 19.3, Vite 8, Vitest 5, Testing Library, TypeScript 6 (strict, `noUncheckedIndexedAccess`), ESLint with `no-explicit-any: error`. **No router, no data-fetching library, no CSS framework, no chart library.**
- `vite.config.ts` has no dev-server proxy. The backend has **no CORS** middleware.

**API** (`backend/guideword/api/app.py`)
- Every endpoint in PROJECT.md §11 runs for real except `GET /demo` (501, Phase 7). With `GUIDEWORD_MOCK=1` every endpoint serves `contract/fixtures/` (mock plant A); overrides are echoed, not stored (`stored: false`).
- Every run-related response carries `label` (`live | recorded | mock`, `recorded_at`, `cost_usd`). A recorded run returns 403 on overrides.
- **`POST /runs` only creates (or resumes) the run; nothing drives it.** Driving is `POST /internal/runs/{id}/advance`, which needs a server secret the browser must never hold. So a run started from the UI today sits at `running` forever (see B2).
- `GET /runs/{id}/events?after=<seq>` returns every event after `seq` with `next_after`; no page limit.
- `GET /runs/{id}/records/{record_id}` returns finding, hypothesis, question, section, chain, LOPA, recommendation, override and model-call records with parents and calls. Evidence records and agent steps are addressable since PR 5c (#97); tool calls (`tc:`) are not (B3).
- `GET /plants/{id}` returns `facts` (one `PlantFact` per stated field, with value and source, e.g. `L-B-SIN.from_id`, `HV-B-SIN.normal_position`, `EA-425B.design_pressure_kpa`) and `sections`. Enough to draw the plant and to resolve every fact link.
- `GET /runs/{id}/export.xlsx` streams the worksheet; `GET /runs/{id}/export/run.json` the dump.

**Events (the live timeline's data): the fixture does not match the backend.**

| Event | `contract/fixtures/events_page.json` payload | What the backend emits |
|---|---|---|
| `agent_decision` | `agent_step_id, tool, reason` | `step_id, agent, tool, reason` |
| `model_call` | `model_call_id, tier` | `model_call_id, job, model_id, cache_hit, outcome, cost_usd, cap_cost_usd` (+ `fell_back_from`); **no tier** |
| `tool_call` | `tool_call_id` | `tool_call_id, tool, refused` |
| `dispatch` | `agent, question_ids` | `agent, level, question_ids, selected_by_code, priority, skipped, batches, admission{…}` |
| `finding_added` | `finding_id` | `finding_id, question_id, tier` |
| `coverage_updated` | `checked, total` | `lines: [CoverageList…]` |
| `step_finished` | `step` | `step, status, next_step` + the step's summary |
| `chain_added`, `lopa_done` | id only | id + `links` / `complete`, … |

`Event.payload` is an untyped dict in the contract, so TypeScript can't catch this. A timeline built on the fixture would break on the first real run.

## In scope

### 5.0 Shell, data layer and conventions (`src/app/`, `src/api/`, `src/format/`, `src/ui/`)
- **Routes (hash):** `#/plants`, `#/plants/:plantId` (plant input), `#/plants/:plantId/sections`, `#/runs`, `#/runs/:runId/live`, `#/runs/:runId/shortlist`, `#/runs/:runId/items/:targetId`, `#/runs/:runId/worksheet`, `#/runs/:runId/coverage`. IDs URL-encoded (they contain `:`).
- **Header:** plant and run selectors, the run's **label banner** (live / recorded with date and cost / mock), status and step, spend so far vs cap (`GET /runs/{id}`), engineer name, budget (`GET /budget`).
- **API client** `src/api/client.ts`: typed from `types.ts` only (`paths`/`components`), base URL from `import.meta.env.VITE_API_BASE` (default same origin). Errors mapped to one `ApiError` with `status`, `detail`, `phase`: 501 → "Not built until Phase <n>"; 403 → "This run is recorded and read-only"; 404 → not found; 409 → the server's reason (e.g. "sections not confirmed", "cap reached"); network → retry button.
- **Hooks:** `useResource(path)` (load, error, reload), `usePolling(path, everyMs, while)` (stops when the run ends or the tab is hidden), `useEvents(runId)` (live mode by `next_after`; replay mode per P5-4).
- **Fixtures in tests:** tests import `contract/fixtures/*.json` directly (add `resolveJsonModule` to `tsconfig.json`; the Vite/Vitest config allows reading `../contract`), typed as the generated response types, so a fixture that drifts from the contract fails `typecheck`.
- **Detail scope:** the detail route is for shortlist targets (findings, chains, hypotheses on the shortlist). Any other record (a worksheet row's finding, a question, a model call) opens in the record drawer instead.
- **Dev proxy:** `vite.config.ts` proxies `/plants`, `/runs`, `/budget`, `/demo` to `http://127.0.0.1:8000` (no CORS change). Same-origin in Phase 7.
- **Formatters:** `src/format/number.ts` (P5-5), `src/format/time.ts`, `src/format/ids.ts` (short display of long IDs with the full ID in the drawer and a copy button).
- **Primitives:** `Traced` (P5-6), `RecordDrawer`, `Chip` (severity, tier, verdict, origin, status), `Flags` (renders `ShortlistItem.flags` and `Evidence.flags` verbatim), `CostLine`, `ConfirmInline`.
- Business rules stay out of components (CLAUDE.md §9): pure functions in `src/model/` (e.g. timeline grouping, plant graph layout, worksheet filtering), each tested.

### 5.1 Screen 4 — Shortlist (`#/runs/:runId/shortlist`)
Source: `GET /runs/{id}/shortlist` (+ `/runs/{id}` for the header).
- Three tier groups in order: **Confirmed** (hypothesis rank shown), **Also found**, **Unconfirmed** (`target_kind: hypothesis`, "not confirmed by the checks — engineer to review"). Within a tier, the server's order (`rank`); the UI never re-sorts.
- Card: target kind (finding / chain / hypothesis), multi-failure badge, unsure badge, lead text (finding consequence, chain description, or hypothesis mechanism), severity chip, `gap_text` (or "no LOPA" with the flag text), up to 3 evidence verdict chips with their summaries, recommendation count and states, every flag verbatim, override state.
- Click → finding detail. Keyboard navigable list.

### 5.2 Screen 5 — Finding detail (`#/runs/:runId/items/:targetId`)
Source: the shortlist item for `targetId` (from the cached shortlist) plus `GET /records/{id}` for drill-down, `GET /plants/{id}` for facts.
- **What:** for a chain, its description, reason, ordered links — each a finding (consequence, cause, failing components, severity) or a plant fact (value + source) — and its flags; for a finding, question, cause, failing components, consequence, existing safeguards, confidence; for a hypothesis, mechanism, components and reason.
- **Supporting findings** (confirmed lines): `support_finding_ids`, each traced.
- **LOPA:** initiating event and frequency (flagged "assumed" when it is), each candidate layer as a row: layer ID and type, **Ultra's** yes/no and argument (`applies`, `argument`) kept visually apart from **code's** credit and reason (`credited`, `pfd`, `reason`), refused layers styled per P5-10; mitigated and tolerable frequencies; `gap_text`; modifiers not applied with their reason; LOPA flags; `complete: false` shows its `missing_fact_ids` as traced facts.
- **Evidence:** one card per record: kind, verdict chip, summary (verbatim), cited `fact_ids` (traced), sources (links open in a new tab), flags, missing facts; precedent cards show the incident title and URL; the judge's model call is traced.
- **Recommendations:** action, reason, state; Accept / Reject / Edit action (P5-7).
- **Overrides on this target:** accept / reject (finding or chain), edit consequence (finding), change severity (finding or chain, S1–S5 picker with required reason), change credit (per LOPA layer, with the reason "engineer asserts inlet valve managed" shown by the server for relief devices; the UI shows the §23 limit text next to the control). After an override, the item and shortlist reload; the new `gap_text` comes from the server.
- **The demo moment must work end to end on the WG final run** (C2), on the rank-2 startup chain (`ch:EA-425B.design_pressure_kpa+…+f:proc:P-REB-START-2:early…`): chain card → its description shown as stored, with its flag "unexpected character in model text: U+4E92 (chain description)" visible (no cleaning) → the RV-PATH-EA425B layer row with its stored "does not apply" reason → the `HV-B-SIN.normal_position` link opened in the drawer → blocked-in heating evidence "at least 1.6× design" with its cited facts → recommendation → change severity S3 → S4 → the server's new gap text (about 1,000× → about 10,000×) and the server's shortlist order. The override is made in `guideword-demo.db`, never in `guideword.db` (C8).

### 5.3 Screen 3 — Live run (`#/runs/:runId/live`)
Source: `useEvents` (P5-1 typed payloads), `GET /runs/{id}`, `POST /runs/{id}/cancel`.
- **Timeline** (newest at the bottom, auto-scroll unless the user scrolled up): step boundaries (`step_started/finished` with status and summary); the whole-plant pass (`hypothesis_added`/`dropped` with rank and reason); each orchestrator decision (`agent_decision`: agent, tool, one-line reason); each dispatch (agent, level, number of questions, selected by code or by the orchestrator, priority, batches); each model call grouped under its dispatch or step (**tier chip** Ultra / Super / Lightning, job, cache hit, cost); tool calls (tool, refused); findings added (count per dispatch, expandable); chains, LOPA records, evidence as they land; cap hits with their reason; `run_extended` passes; run finished / failed.
- **Side panel:** coverage bars from the latest `coverage_updated.lines`, findings count, spend so far vs cap, model mix (calls and cost per tier, computed from `model_call` events by a pure function).
- **Start a run** from `#/runs` or the plant screen: the use (from `Budget.api_run_uses`) with its remaining amount and the phase's; spend cap and post cap inputs, **never pre-filled**; spend cap + post cap = the maximum, refused when it exceeds either remaining amount; mode `full`; P5-8 confirm; then navigate to live. A run's use and caps are fixed when it starts; a resume with a different one gets a 409 naming the stored value. Cancel button while running.
- **End state:** finished, stopped at the analysis cap, stopped at the post cap, or stopped by the budget, each named (`cap_hit.cap`), with spend against that cap.
- **Replay** per P5-4, chosen automatically for a finished run, with a speed control and a "jump to end".

### 5.4 Screen 7 — Coverage (`#/runs/:runId/coverage`)
Source: `GET /runs/{id}/coverage`, `GET /runs/{id}/questions?…`.
- One row per list (sections, matrix, chemical pairs, chemical environment, no-flow lines, procedure steps, planned work, dust, relief discharge, added by AI, engineer): checked / total bar, unsure, failed. Totals at the top: "checked X of Y".
- Failed questions listed with their IDs (traced) and text.
- **Add an engineer question:** section picker + text → `POST /runs/{id}/questions`; listed as open; answered with the `answer` override from the worksheet or here.

### 5.5 Screen 6 — Worksheet (`#/runs/:runId/worksheet`)
Source: `GET /runs/{id}/worksheet`.
- Table with the §5 Step 8 columns, sticky header, virtualised only if the row count makes it slow (measure on the WG run first; no library unless needed — stop-and-ask).
- Filters: section, guideword, origin (matrix / cross-list / added by AI / engineer), status, override state, "has LOPA gap", free text. Filtering is a pure function, tested.
- Row actions per the override rules (accept / reject / edit consequence or action; answer an engineer question). Each cell's record IDs are traced (`record_ids`).
- **Export:** a link to `/runs/{id}/export.xlsx` and `/runs/{id}/export/run.json`.

### 5.6 Screen 2 — Sections (`#/plants/:plantId/sections`)
Source: `GET /plants/{id}`, `POST /plants/{id}/sections/propose`, `PUT /plants/{id}/sections`.
- **Diagram:** equipment as nodes, lines as edges (`<line>.from_id` / `to_id` facts), utilities and locations as edge endpoints, laid out left-to-right by a pure function (longest-path layering from sources; ties by ID); each section's objects outlined in that section's colour; flagged no-flow sections dashed. Pan and zoom by viewBox; must stay legible for ~20 equipment items (WG has 3, dev cases up to ~20).
- **List:** each section with kind, type, name, purpose, objects, drawn by (rule / suggestion / engineer), suggestion reason.
- **Propose** (P5-8): shows the suggestions with reasons and the **refused** ones with code's reason (v1.3 `rejected`). Accept / reject each; rename; edit purpose; then **Confirm** → PUT. Regrouping existing objects into an engineer section is allowed; a no-flow section can't be merged away (the server refuses; show its reason).

### 5.7 Screen 1 — Plant input (`#/plants`, `#/plants/:plantId`)
Source: `GET /plants`, `POST /plants`, `GET /plants/{id}`.
- Upload a plant JSON file (file input + drag and drop; `FileReader`) → `POST /plants` → errors (blocking) and warnings, each with its object ID.
- Plant facts table: ID, value, source; filters "assumed" and "not stated"; counts at the top ("N facts, M assumed").
- Plant list with status (uploaded / sections proposed / confirmed) and its runs.

## Tests (written first; all $0; `npm run lint && npm run typecheck && npm test`)

- **Formatter:** every P5-5 rule, including float noise (0.010000000000000002 → "0.01"), boundaries, `null`.
- **Router:** every route parses and builds, with IDs containing `:`, `~`, `+`.
- **Client:** each status maps to its message (501 names the phase, 403 read-only, 409 shows the server's detail); no request carries an override on a `recorded`/`mock` label (P5-7).
- **Screens on fixtures:** each screen renders from `contract/fixtures/*.json` (served through a fake fetch) with no console error; tier order kept as served; flags shown verbatim; `gap_text` shown and no gap number formatted by the component; refused layer shows code's reason and Ultra's argument separately.
- **Traceability:** every rendered number in the shortlist and detail fixtures sits inside a `Traced` with an ID (a DOM test walks text nodes with digits).
- **Timeline:** a pure grouping function turns the generated `events_page.json`, `events_page_failed.json` and the four legacy fixtures into the expected groups; model-call tier chips come from the payload's `tier`; replay plays events in `seq` order and never skips or invents one; the replay banner is always present in replay mode.
- **Worksheet filter** and **plant graph layout:** pure functions, tested (layout deterministic for the same facts).
- **Overrides:** the change-severity form sends exactly `{target_id, action: "change_severity", new_value: {severity_class}, reason, by}`; after success the item reloads.
- Backend (B1–B3): as listed in their rows.
